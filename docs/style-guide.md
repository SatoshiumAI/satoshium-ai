# ✍️ Satoshium Documentation Style Guide

This document defines conventions for writing documentation across the Satoshium platform.

Documentation within Satoshium is treated as infrastructure rather than supporting material.  
Consistency enables coordination between repositories, systems, agents, and readers over long time horizons.


---

# 🧭 Purpose

The style guide ensures that documentation across the platform remains:

- structurally consistent
- terminology-aligned
- registry-compatible
- governance-aware
- readable across decades of evolution

It supports interoperability between:

- Manifesto
- Protocol
- Governance
- Registry
- Canon
- Specifications
- Updates
- Simulation layers


---

# 🧱 Core Writing Principles

## Clarity Over Density

Prefer precise language over compressed explanations.

Example:

✔ verifiable coordination surface  
✘ decentralized meta-alignment orchestration layer


## Stability Over Trend Language

Avoid terminology tied to short-lived technology cycles.

Example:

✔ coordination interface  
✘ prompt stack engine


## Structure Over Narrative Drift

Documentation should follow layered architecture logic rather than storytelling flow.


## Neutral Tone

Documentation should describe systems without marketing language.

Example:

✔ experimental simulation environment  
✘ revolutionary simulation platform


---

# 🧠 Terminology Conventions

Use consistent vocabulary across repositories.

Preferred terms:

| Concept | Term |
|--------|------|
| platform-wide architecture | coordination infrastructure |
| intelligent components | agents |
| experimental environments | simulations |
| shared vocabulary layer | glossary |
| canonical definitions | Canon |
| system identifiers | registry IDs |

Avoid introducing alternate synonyms unless necessary.


---

# 🗂️ System Identifier Formatting

Always reference registry systems using their canonical identifiers.

Example:

SYS-GOV-002
SYS-KNOW-001
SYS-SIG-001


Do not rename or abbreviate identifiers.

Identifiers act as long-term coordination anchors.


---

# 📚 Document Structure Standards

Preferred order for architecture documents:

1. Purpose
2. Principles
3. Layer relationships
4. Registry integration
5. Governance compatibility
6. Domain architecture
7. Long-term direction
8. Status


---

# 🔐 Governance-Compatible Language

Documentation should remain compatible with verification-aware systems.

Prefer:

- inspectable
- registry-addressable
- verifiable
- modular
- layered
- deterministic

Avoid:

- opaque
- proprietary logic descriptions
- hidden evaluation assumptions


---

# 📡 Domain Reference Conventions

When referencing platform domains, use canonical descriptions.

Example:

| Domain | Role |
|-------|------|
| satoshium.ai | public architecture layer |
| satoshium.info | knowledge and engineering layer |
| satoshium.xyz | experimental frontier |
| satoshium.net | infrastructure coordination layer |
| satoshium.store | cultural and economic surface |
| satoshium.link | shared component gateway |

Do not redefine domain roles inconsistently across repositories.


---

# 🧩 Repository Reference Conventions

Repositories should be described as platform modules rather than standalone projects.

Example:

✔ contributes to the Knowledge Layer  
✘ independent glossary project


---

# 🧪 Simulation Documentation Rules

Simulation layers must be described as exploratory environments.

Preferred wording:

- scenario modeling
- coordination testing
- signaling environments
- experimental infrastructure surfaces

Avoid describing simulations as production systems.


---

# 📎 Registry Alignment Requirements

When documenting systems listed in:

Agent Governance Tool (SYS-GOV-002)
Layer: Governance Systems
Status: Operational



---

# 🛡️ Canon Compatibility

Documentation should remain compatible with Canon constraints.

This includes:

- terminology consistency
- neutral tone
- layered reasoning structure
- avoidance of speculative authority claims


---

# 🔭 Long-Term Documentation Expectations

Satoshium documentation is designed to remain readable and useful across long time horizons.

Documents should therefore be:

- modular
- referenceable
- registry-compatible
- domain-aligned
- governance-aware
- version-resilient
